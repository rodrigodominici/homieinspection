- Contractors never read inspections rows directly: they get property summary via SECURITY DEFINER contractor_inspection_summaries, contact field values are excluded by RLS, and tenant info is shared only through executive-written inspection_work_orders.contractor_message. Why: OT recipients must not see tenant or owner personal data.
- Final quotation settlements (finiquito) are immutable versioned rows in quotation_final_settlements created only via create_final_settlement for in_review/approved OTs, using owner prices, final quantity capped at approved, pending quotes excluded. Why: billing must reflect executed work without rewriting the approved quotation.
- An inspection may have several work orders (one per contractor); a repair item can be active in only one OT (partial unique index), extra OTs are created via assign_additional_work_order with unassigned approved items, and inspection work_status is recomputed across all OTs. Why: multiple providers must not duplicate work or close the inspection early.
- Contractor extra-work proposals live in work_order_proposals (contractor inserts pending rows for own open OTs; staff decide via decide_work_order_proposal, which creates a repair item with the owner price); proposal-born items reach an OT only after the investor's latest decision is accepted (repair_item_ready_for_work). Why: extra work must not bypass investor approval.
- Execution report versions are immutable snapshots in work_order_execution_reports created only via create_execution_report_version (staff), storing photo paths that are signed at download time. Why: downloaded history must not change when the contractor edits later.
- Final inspection: per-item cumple/no cumple lives in append-only work_order_final_checks via record_final_check; 'no cumple' reopens the OT (status rejected) instead of editing completed items. Why: completed work is immutable and every verdict stays as evidence.
